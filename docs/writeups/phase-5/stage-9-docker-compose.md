# Phase 5, Stage 9 - Docker-compose `api` service + phase overview

## What is being implemented

The first `Dockerfile` in this project (repo root) and a new `api` service in `docker-compose.yml`, alongside the existing `postgres`/`minio` services.

The `Dockerfile` is `python:3.12-slim`-based: installs `uv`, copies `pyproject.toml`/`uv.lock`/`README.md`/`src/`, runs `uv sync --no-dev --frozen`, and runs `uv run uvicorn sloppy.api.app:app --host 0.0.0.0 --port 8000`. A new `.dockerignore` excludes `.venv`, `.git`, test/doc/data directories, and `models_artifacts` from the build context.

The `api` compose service builds from that Dockerfile, publishes `${API_PORT:-8000}:8000`, loads `.env` via `env_file`, then overrides `POSTGRES_HOST=postgres` and `S3_ENDPOINT_URL=http://minio:9000` (the compose-internal DNS names for the other two services - `.env`'s own defaults are `localhost`-oriented, correct for the day-to-day dev workflow of running `uv run uvicorn` directly on the host, but wrong once the API itself is containerized on the same Docker network as `postgres`/`minio`). It `depends_on` both other services with `condition: service_healthy`, and has its own healthcheck (a plain Python `urllib.request` call to `/health`, avoiding a dependency on `curl` being present in the `python:3.12-slim` base image).

## What it should look like

```
$ docker compose up --build api
# ... build output, then:
api-1  | INFO:     Uvicorn running on http://0.0.0.0:8000

$ docker compose ps
NAME              STATUS
slop-postgres-1   Up (healthy)
slop-minio-1      Up (healthy)
slop-api-1        Up (healthy)

$ curl http://localhost:8000/health
{"status":"ok"}

$ curl http://localhost:8000/videos
{"items": [], "total": 0, "limit": 20, "offset": 0}
```

An empty `items`/`total: 0` response from the containerized API is equally valid proof of correct wiring as a populated one - it confirms the `api` container is genuinely talking to the real `postgres` service over the compose network, not erroring out or silently pointing at nothing.

Day-to-day development is unaffected by any of this: `uv run uvicorn sloppy.api.app:app --reload --port 8000`, run directly on the host against the already-published `postgres`/`minio` ports, remains the primary way to iterate (as it was for every stage in this phase) - `docker compose up --build api` is a "does the container build and boot" check, not the everyday workflow. `uv run pytest` also continues to run directly on the host, unchanged.

## A real bug found and fixed

The first build/boot smoke test revealed a genuine bug, not a hypothetical: the Dockerfile's original `CMD ["uv", "run", "uvicorn", ...]` looked correct, but `docker compose logs api` on startup showed `uv run` silently re-syncing the environment every time the container started - `Downloading ruff`, `Downloaded virtualenv`, `Installed 12 packages` - re-installing the dev dependency group (`ruff`, `pytest`, `httpx`) that the build step's `uv sync --no-dev --frozen` had deliberately excluded. `uv run` re-syncs the project environment against `pyproject.toml`/`uv.lock` by default on every invocation, regardless of how the environment was built - `--no-dev` only affected the explicit build-time `uv sync` call, not the implicit sync `uv run` performs at container start. Fixed by adding `--no-sync` to the runtime `CMD` (`uv run --no-sync uvicorn ...`), which uses the already-built venv exactly as-is with no re-sync check and no network access needed at container start. Rebuilt and re-verified: the container now starts cleanly straight into `Uvicorn running on http://0.0.0.0:8000` with no package-install noise, and `/health`/`/videos` both still respond correctly.

## What to look out for

- **This resurfaces Stage 4's presigned-URL caveat, and it's the single most important gotcha in this whole phase.** A presigned thumbnail URL generated by the containerized `api` service (resolving MinIO at `http://minio:9000` on the compose network) will embed that hostname - meaningless to a browser on the host machine, which can only reach MinIO at `http://localhost:9000`. This means: **if you run the API via `docker compose up api`, thumbnail images will not load in a browser**, even though every other part of the response (scores, feature breakdowns, similar videos) will be completely correct. This is left as an explicit, accepted follow-up for a later phase (e.g. a separate public-facing endpoint setting used only for presigning, or a reverse proxy) - not solved here. Running the API via plain `uv run uvicorn` on the host does not have this problem, since `.env`'s `S3_ENDPOINT_URL=http://localhost:9000` is directly reachable from a browser on the same machine.
- **This Docker image is large** (~2-3GB, in the same range as Phase 4's TODO.md disk-footprint note) because `torch`/`transformers`/`sentence-transformers` are full production dependencies in `pyproject.toml`, not dev-only - even though the API itself never imports any ML-model code directly in Phase 5 (feature computation happens via the `slop features compute-nlp`/`compute-vision` CLI commands, not through any API endpoint). Splitting a lighter API-only dependency group is a reasonable future optimization, explicitly not attempted in this phase.
- **`uv sync --no-dev --frozen`** in the Dockerfile intentionally skips `ruff`/`pytest`/`httpx` (the dev group) from the runtime image, and `--frozen` ensures the build fails loudly rather than silently re-resolving if `uv.lock` and `pyproject.toml` ever drift out of sync inside CI/a clean clone.
- No volume-mounted live-reload dev setup was added for the `api` service - it's a from-scratch image build every time, matching the "keep it simple" bias of a demo project rather than optimizing a container-based inner dev loop that isn't actually being used day to day.

## How to run tests properly

```powershell
# Container build/boot smoke test (postgres/minio must already be healthy)
docker compose up -d postgres minio
docker compose up --build api
curl http://localhost:8000/health
curl http://localhost:8000/videos
docker compose ps

# The actual test suite is unaffected and still runs on the host, not in the container
uv run pytest
uv run ruff check .
uv run ruff format --check .
```

There is no new automated test for the Docker build itself (building and running a container isn't something `pytest` exercises) - this stage's verification is the manual `docker compose up --build api` + `curl` sequence above, which was actually run (not just described): the image built successfully, the container reached `healthy` status, `/health` returned `{"status":"ok"}`, and `/videos` returned `{"items":[],"total":0,"limit":20,"offset":0}` against the real (empty) dev Postgres - confirming genuine end-to-end wiring, not just a config that looks right on paper. The container was stopped afterward (`docker compose stop api`) since it's a smoke test, not meant to stay running as part of the normal dev loop.
