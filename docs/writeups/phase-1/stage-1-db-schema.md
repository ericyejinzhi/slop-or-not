# Phase 1, Stage 1 — DB schema: SQLAlchemy models + Alembic migration

## What is being implemented

The persistence layer for Phase 1: four Postgres tables (`channels`, `videos`, `comments`, `thumbnails`) defined as SQLAlchemy 2.0-style ORM models, plus Alembic wired up to generate/apply/reverse migrations against them. No data flows yet — this is schema only.

Files: `src/sloppy/db/base.py`, `models.py`, `session.py`; `alembic.ini`, `alembic/env.py`, `alembic/versions/ae9544f5d4ed_initial_schema.py`; `tests/test_db_models.py`.

## What it should look like

- `psql \d channels` / `\d videos` / `\d comments` / `\d thumbnails` should show the columns as designed (text PKs matching YouTube's own ids, `text[]` arrays for `topic_categories`/`tags`, FKs `videos.channel_id → channels.id`, `comments.video_id → videos.id`, `thumbnails.video_id → videos.id`, and a unique index on `channels.handle`).
- `uv run alembic current` should print `ae9544f5d4ed (head)`.
- `uv run pytest` should show 4 passing tests (2 pre-existing config tests + 2 new ones checking all 4 tables are registered on `Base.metadata` and FKs point where expected).
- `uv run slop smoke` should still pass unchanged — this stage shouldn't touch the Phase 0 connectivity checks.

## What to look out for

- The new ORM models live in `src/sloppy/db/`, *not* `src/sloppy/models/` — that package name is already reserved for the Phase 3-4 ML models per its docstring, so this avoids a future collision.
- Every table's primary key is YouTube's own id (channel id, video id, comment id) rather than a surrogate integer. This is a deliberate bet that makes Stage 5's idempotent upsert simple (`ON CONFLICT (id) DO UPDATE`) — but it means these tables can never hold anything that isn't sourced from YouTube.
- The migration file is autogenerated (`ae9544f5d4ed_initial_schema.py`, hash-named — that's Alembic's normal convention, not a mistake) and then run through `ruff format`/`ruff check --fix`. The generated DDL was reviewed before applying; it matched the model definitions exactly.
- `uv` was not on PATH by default in this environment — it had to be located under `%LOCALAPPDATA%\Microsoft\WinGet\Packages\astral-sh.uv_...` and prepended manually. A fresh terminal opened after the original winget install should resolve `uv` normally (per `DEVIATIONS.md`).

## How to run tests properly

```powershell
# 1. Make sure Postgres/MinIO are up
docker compose up -d

# 2. Run the test suite
uv run pytest

# 3. Confirm migration state and inspect the schema directly
uv run alembic current
docker compose exec postgres psql -U slop -d slopornot -c "\d channels" -c "\d videos" -c "\d comments" -c "\d thumbnails"

# 4. Confirm the migration is reversible (optional but worth doing once)
uv run alembic downgrade -1
uv run alembic upgrade head

# 5. Confirm Phase 0 didn't regress
uv run slop smoke
```
