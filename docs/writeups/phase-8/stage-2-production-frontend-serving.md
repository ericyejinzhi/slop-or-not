# Phase 8, Stage 2 - Production frontend serving (nginx)

## What is being implemented

Phase 6 built the React app's dev workflow (`npm run dev`, Vite's own dev-server proxy) and a production build (`npm run build` -> a static `dist/`), but nothing served that static build anywhere - there was no container, no web server config, no way to actually deploy the frontend as the roadmap's "API + frontend -> single EC2 with docker-compose (simplest)" path calls for.

- **`web/Dockerfile`** - a multi-stage build: stage 1 (`node:24-alpine`) runs `npm ci && npm run build`; stage 2 (`nginx:alpine`) copies only the built `dist/` output and a config file - the Node toolchain and `node_modules` never ship in the final image.
- **`web/nginx.conf`** - two `location` blocks: `/` serves the static SPA with `try_files $uri $uri/ /index.html` (so a hard refresh on a client-side route like `/videos/abc123` doesn't 404 - nginx doesn't know about React Router's routes, so it falls back to `index.html` and lets the client-side router take over); `/api/` reverse-proxies to `http://api:8000/`, stripping nothing extra - **the exact same shape as the Vite dev server's own `/api` proxy** (`web/vite.config.ts`, Phase 6 Stage 3). The frontend's `BASE_URL = '/api'` in `web/src/api/client.ts` never needed to change - it works identically talking to Vite's dev proxy or this nginx config.
- **New `web` service in `docker-compose.yml`**, built from `./web`, published on `${WEB_PORT:-8080}`, depending on `api`'s healthcheck.
- **A stale comment fixed in passing**: the `prefect-server` service's comment still said flow code "runs in a worker via `uv run prefect worker start`" - corrected to `uv run slop orchestrate serve`, matching the actual mechanism decided back in Phase 7 Stage 6. Left uncorrected, this would have quietly pointed at a Prefect concept this project doesn't actually use.

## What it should look like

```
$ docker compose up -d --build api web
$ curl http://localhost:8080/
200   # nginx serving the built React app

$ curl http://localhost:8080/api/health
{"status":"ok"}   # proxied through to the real api container

$ curl http://localhost:8080/api/videos
{"items":[],"total":0,"limit":20,"offset":0}   # real backend response, real (empty) DB

$ curl -o /dev/null -w "%{http_code}\n" http://localhost:8080/videos/abc123
200   # NOT a 404 - nginx's try_files fallback hands this to index.html, React Router
      # then renders VideoDetailPage client-side
```

All four of these were actually run against real, freshly-built containers - not described hypothetically. Both `slop-or-not-api` and `slop-or-not-web` images were built from scratch, both containers reached a running/healthy state, and all four checks passed exactly as shown.

## What to look out for

- **This closes the exact gap Phase 5 Stage 4/9 and Phase 6 flagged repeatedly as a known, deferred limitation**: presigned thumbnail URLs generated by a containerized API embed whatever `S3_ENDPOINT_URL` that container resolves (`http://minio:9000` inside compose) - unreachable from a host browser. That specific problem is about the **API's own presigned URLs**, and is still not solved by this stage (still real, still deferred, still documented) - this stage is about getting the **frontend application itself** servable and correctly proxying to the API, which is a separate concern that this stage does fully solve.
- **`try_files $uri $uri/ /index.html` is what makes client-side routing survive a hard refresh** - without it, nginx would look for a literal file/directory at `/videos/abc123` on disk, find nothing, and return its own 404 page instead of ever loading the React app to let React Router handle the route. This is standard, necessary SPA-serving configuration, not an aesthetic choice.
- **The nginx `/api/` proxy hardcodes the compose service name `api`** (`proxy_pass http://api:8000/`) - this only resolves inside the docker-compose network. A real EC2/production deployment using this same `docker-compose.yml` would work identically (both containers on the same compose network, same service names), but a different deployment topology (e.g. `web` and `api` as separate ECS services, or `web` deployed to S3+CloudFront per the roadmap's "optionally" alternative) would need this proxy target reconsidered - noted here, not solved, since only the docker-compose/EC2 path was in scope for this stage.
- **No automated test covers the Docker build/serve path itself** (matching the precedent set by every prior phase's own docker-compose smoke-test stages, e.g. Phase 5 Stage 9's `api` service) - `npm run build`/`npx vitest run`/`npm run lint` (Phase 6) already cover the application code; this stage's own verification is the real container build-and-curl sequence shown above.

## How to run tests properly

```powershell
docker compose config --quiet        # validates docker-compose.yml syntax
docker compose up -d --build api web
curl http://localhost:8080/
curl http://localhost:8080/api/health
curl http://localhost:8080/api/videos
curl -o /dev/null -w "%{http_code}\n" http://localhost:8080/videos/abc123
docker compose stop api web           # not needed to stay running day-to-day

# Application-level tests (unaffected by this stage - no application code changed)
uv run pytest                         # 182 passed, 5 deselected
cd web && npx vitest run              # 52 passed
```
