# Phase 8, Stage 3 - Reference Terraform IaC

## What is being implemented

A new `infra/terraform/` directory: real, syntactically valid Terraform describing exactly the resources `ROADMAP.md`'s Phase 8 calls for - an S3 bucket (`s3.tf`), an RDS Postgres instance (`rds.tf`), and a single EC2 instance running `api`+`web` via docker-compose with an IAM instance role for S3 access (`ec2.tf`), plus shared provider/data-source config (`main.tf`), inputs (`variables.tf`), and outputs (`outputs.tf`).

**This was never `terraform apply`d and provisions nothing** - per the confirmed Phase 8 scope, this is reference architecture only. Terraform's CLI (`1.16.2`, installed fresh via `winget` specifically for this stage - it wasn't present in this environment before) was used to genuinely validate the configuration locally: `terraform init -backend=false` (downloads the AWS provider plugin, no account needed), `terraform fmt -check -diff` (canonical formatting, passed with zero changes needed), and `terraform validate` ("Success! The configuration is valid.") - all real, all passing, all requiring zero AWS credentials. A `terraform plan` was also attempted, deliberately, to confirm exactly where the boundary of "code-only" verification actually sits.

## What it should look like

```
$ cd infra/terraform
$ terraform init -backend=false
Terraform has been successfully initialized!

$ terraform validate
Success! The configuration is valid.

$ terraform plan -var="db_password=placeholder"
Error: No valid credential sources found
...dial tcp 169.254.169.254:80: connectex: A socket operation was attempted to an
unreachable network.
```

That last failure is exactly the expected and correct outcome - it proves the configuration itself parsed, validated, and got as far as attempting to talk to a real AWS account before failing, precisely because no such account exists here. This is the cleanest possible confirmation that the Terraform is genuinely sound rather than untested, without crossing into actually needing (or risking) real AWS access.

## What to look out for

- **A `.terraform.lock.hcl` file was generated by `terraform init` and is meant to be committed** (it pins the exact AWS provider version, `~> 5.0` resolved to `5.100.0`, for reproducible future `init` runs) - unlike the `.terraform/` directory itself (downloaded provider binaries, correctly gitignored via a new `infra/terraform/.gitignore`) and any hypothetical `*.tfstate`/`*.tfvars` files (also gitignored, defensively, even though none exist yet since nothing has ever been applied).
- **Every security-relevant default is deliberately non-functional, not just "a reasonable default"**: `ssh_ingress_cidr` defaults to `203.0.113.1/32` - an RFC 5737 documentation-only address that will never route on the real internet - specifically so a future `terraform apply` can't accidentally leave SSH open to the whole world if someone forgets to override it; `thumbnails_bucket_name` defaults to an obviously-placeholder string (`slop-or-not-thumbnails-CHANGE-ME`) rather than a name that might collide with a real bucket someone else already owns (S3 bucket names are unique across all of AWS, not just one account); `db_password` has no default at all, forcing an explicit `-var`/`TF_VAR_`/tfvars value rather than ever risking a hardcoded password living in version control.
- **`user_data` (the EC2 instance's boot-time provisioning script) was deliberately left unset**, with the real deployment steps (install Docker, clone the repo, configure `.env`, `docker compose up -d --build api web`) written as prose in this stage's README instead of baked into Terraform as an unreviewed, never-run shell script. Automating that later is a reasonable follow-up, once someone is actually about to apply this for real and can review/test the script against a real instance.
- **Enabling the `pgvector` extension on the RDS instance is explicitly out of Terraform's scope** - `CREATE EXTENSION vector;` is a SQL statement that only makes sense once the database exists, not an AWS resource. This is called out in the README and tracked as a manual step in `docs/writeups/TODO.md`, the same way every other "provision, then do one manual thing" step in this project has been handled (e.g. Phase 4's HuggingFace model downloads, Phase 6's Node.js requirement).
- **The IAM policy granted to the EC2 instance role is scoped to exactly 3 S3 actions on exactly 1 bucket** (`GetObject`/`PutObject`/`ListBucket` on the thumbnails bucket ARN and its contents) - not a wildcard `s3:*` on `*`, matching the actual, real permissions `src/sloppy/storage.py`/`src/sloppy/ingest/thumbnails.py` need and nothing more.

## How to run tests properly

```powershell
cd infra/terraform
terraform init -backend=false
terraform fmt -check -diff
terraform validate
terraform plan -var="db_password=placeholder"   # expected to fail on missing credentials
```

No automated pytest coverage applies here - this is infrastructure configuration, not application code, and its own tooling (`terraform validate`/`fmt`) is the correct verification layer, exactly as `docker compose config --quiet` was for `docker-compose.yml` in this phase's Stage 2. `uv run pytest` (184 passed, 5 deselected) is unaffected - no Python code changed in this stage.
